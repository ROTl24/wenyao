# Agent Note: 桌面正式生成不设置固定总时限

Status: implemented

## Problem

Electron 正式解读和追问通过 OpenAI Chat 兼容接口读取完整 JSON 响应。固定 180 秒总时限无法区分仍在服务端推理的有效请求与已经停滞的连接；当推理模型不再受应用输出 Token 上限截断时，合法请求可能超过该时限并被客户端主动中止。响应正文读取阶段的中止又位于错误归类边界之外，会把底层英文 `TimeoutError` 直接显示给用户。

## Decision

Electron 正式解读和追问不创建应用侧固定总时限，由服务商、网络栈或用户关闭应用决定请求何时结束。生成模型最小测试、向量建库、查询向量化和重排继续使用各自的有限时限；这些短请求的可用性目标与正式长文本生成不同。

Provider 将建立连接和读取完整响应正文纳入同一网络错误边界。`AbortError` 与 `TimeoutError` 统一转换为中文 `AI_TIMEOUT`，提示先核对服务商用量后手动决定是否重试；任何失败都不会触发自动重试。

PWA 继续使用流式传输的分层边界：最多等待 3 分钟收到首段数据，流开始后以连续 90 秒没有新数据判定中断，持续活跃的流没有固定总时长。桌面 JSON 响应在正文完成前没有可靠的活动信号，因此不使用累计时长替代停滞判断。

## Alternatives considered

- 把桌面总时限提高到更大的固定值：只能把误中止推迟，不能区分长推理和停滞连接。
- 超时后自动重试：服务商可能已经完成部分计费，透明重试会产生重复调用和费用。
- 恢复正式输出 Token 上限或统一关闭思考：会重新引入正文被截断，或改变用户选择的模型行为。
- 强制所有桌面 OpenAI 兼容服务改用 SSE：部分外部兼容接口只保证 JSON 响应，不能在一次付费请求失败后安全回退到第二次调用。

## Consequences

复杂模型可以在超过 180 秒后继续完成正式解读或追问。连接永久停滞时，桌面界面可能持续等待，直到底层网络报告失败或应用被关闭；关闭应用只会停止本机接收，不能证明服务商已经取消处理。服务商自身的上下文、输出、任务和连接时限仍然生效。

如果外部协议提供可靠的流活动、任务状态或幂等取消能力，应优先引入可观测的停滞边界和显式取消，而不是恢复固定总时限。

## Verification

- Electron Runtime 故障注入把固定总时限替换成立即中止信号，确认正式解读和追问均不会再创建该信号。
- Electron Provider 在响应正文读取阶段抛出 `TimeoutError` 时返回中文 `AI_TIMEOUT`，并断言只发起一次请求。
- 完整 Renderer 与 Electron 测试、类型构建、PWA 构建和静态产物校验覆盖未受影响的探测、检索与网页流式边界。
